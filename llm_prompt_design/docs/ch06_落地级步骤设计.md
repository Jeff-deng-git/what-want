## 0. 本章在全书旅程里的位置

- **全书定位**：第 6 章，三支柱「喜欢 × 擅长 × 重要」中的 **「喜欢的事」** 轴（ch04=重要、ch05=擅长、ch06=喜欢）。
- **上游依赖**：练习本身**无硬性上游**（step_context = []，step 不读任何前章档案），可独立进入。但 `mentor_hooks.references=["talents","likes"]` 引用 ch5 的 `talents`，让刘老师开场回响「你第五章写了擅长之事…」，建立 ch5→ch6 连续性；`reference_talents` 输入项引用 ch5 擅长之事做「关联擅长」功能（可选，缺失时面板置灰不阻断）。
- **下游消费**：ch06 产出 `likes` 进入 `learner_profile`，在 ch07 与 ch05 `talents`、ch04 `work_purpose`（过滤器，筛「真正想做 / 作为兴趣」）+ `values`（核心价值观）组合，形成「真正想做的事」。精确契约见 §8.5（含 ch07 上游门禁与 `stale=0` 过滤）。
- **范式**：沿用 ch05「2 步 + 抽屉」轻量工作流；**不新增业务表、不新增 `likes` 专用表**，但为支持上游重提交后的过期隔离，在既有 `step_runs` 表新增 `stale INTEGER NOT NULL DEFAULT 0` 列（一次向后兼容的 SQLite 迁移，沿用 `app/db.py init_db()` 的 `ALTER TABLE ... ADD COLUMN` 幂等补列机制，见 §8.1 / §8.4）。持久键 `likes` 仍在 compaction 白名单，零新增业务字段。

## 1. 一句话目标

帮用户找到「因为兴趣所以喜欢」的事，并把每条拆成 **领域 × 喜欢的方面**，可选地关联 ch5 的擅长之事，形成可迁移到 ch7 组合的《喜欢的事清单》。

---

## 2. 「一步还是多步」先说清（最关键）

**多步（2 步）**，与 ch05 同构，但级联关系不同：

- **step-1「回答 5 个问题」**：逐题长文作答，LLM 映照出初步「喜欢的事」**领域**清单（`likes`，item={text, locked, source}；**step-1 不拆方面、不关联擅长**）；可选追加「热情 30 问」回答（`passion_questions`，来自题库服务）作为补充发现素材，与 q1–q5 一并喂给 step-1 LLM。
- **step-2「整理《喜欢的事清单》」**：`references.from_exercise=step-1` 注入 step-1 领域，LLM 把每条拆成 **领域 × 喜欢的方面**，并关联 ch5 擅长之事；产出结构化 `likes`（item={field, aspects[], linked_strengths[], sources[], locked}）+ `commentary`。

> 与 ch05 对照：ch05 两级联是「talents（无评级）→ talents（带◎〇△）」；ch06 是「likes（仅领域）→ likes（领域+方面+关联）」。两级联都是**同一输出键在 step-2 变丰富**，落库以 submitted 的 step-2 为准。

- `mentor_hooks.references=["talents","likes"]` 仅供导师对话，绝不进入 step prompt（与 ch03/ch04/ch05 同构的 `step_context` 解耦）。
- 状态机同构：运行 LLM → `saved` 草稿 → 编辑/锁定 → `/submit`（`submitted`，不再调 LLM；`edit_output` 返回 409）。
- **级联门禁（submitted-only）**：step-2 的 `references.from_exercise=step-1` 仅读取 step-1 `submitted` 输出（运行时 `_load_prior_outputs` 只查 `status='submitted'`）；step-1 仅 `saved` 未提交时，step-2 运行被拦截并提示「请先提交第一步」。step-1 重新提交后，既有 step-2 结果标记为「已过期，请重新运行第二步」，不自动合并（用户草稿 `reference_talents`/`passion_seeds` 仍可保留）。

## 3. 步骤流程图

```
[进入 ch06] ──► Step 1：回答 5 个问题（q1–q5 多行文本）
              │  + 可选「热情 30 问」追加回答（passion_questions，题库服务）
                    │ 提交（/run：LLM 映照，q1–q5 + passion_questions 共同作为发现素材）
                    ▼
              commentary（合理性陷阱提醒，readonly）+ likes（领域草稿，editable_list）
                    │ 进入 Step 2（references.from_exercise=step-1 注入 likes；需 step-1 已 submitted）
                    ▼
        Step 2：整理《喜欢的事清单》
          ├─ 引用 ch5 擅长之事 → reference_talents（list_of_items，对象数组[{text}]）
          ├─ 引用 100 例清单 → ui_context.passion_examples（抽屉，前端读 config）
          │ 提交（/run：LLM 拆解领域→方面 + 关联擅长）
          ▼
        likes（field/aspects/linked_strengths/sources/locked）+ commentary
                    │ 锁定 / 编辑 / 重新生成（preserve_output 保留 locked）
                    ▼
                 /submit → submitted → compaction 并入 learner_profile.likes
                    │
                    ▼
              ch07 取 喜欢×擅长×重要 交集
```

## 4. 逐阶段明细

### 4.1 Step 1：回答 5 个问题，找出喜欢的事
- **输入**（config `input_schema`）：`q1..q5` 五个 `text` 必填长文框（见 PRD §1.2 原书五问）；可选 `passion_questions`（`list_of_items`，item={`question_id`(q_order 数字), `question`(题目原文，可选), `answer`(用户回答)}）来自「热情 30 问」题库，运行前由前端按 q_order 从 questions 服务取回填入，作为补充发现素材与 q1–q5 一并喂给 LLM。
- **运行**（/run）：LLM（`psychologist`）只映照、不判断，提炼 `likes`（领域数组，item={text, locked:false, source:qN}），并产出 `commentary`（markdown，含 per-question 领域 + **合理性陷阱提醒**）。
- **契约要点**：
  - 不臆造未提及领域；输出严格 JSON；10+ 为引导目标，素材不足不强凑。
  - `commentary` = `readonly`，用户不可编辑。
  - Step-1 的 `likes` 仅含 `text`，**不含 aspects / linked_strengths**（那两项由 step-2 引入）。

### 4.2 Step 2：整理《喜欢的事清单》
- **级联注入**：`references.from_exercise=step-1, fields=["likes"]`，把 step-1 领域注入本步上下文。
- **输入 scratchpad**（config `input_schema`）：
  - `reference_talents`（list_of_items，item={text}，可选）：用户从 ch5《使用说明书》引用擅长之事。**canonical payload = 对象数组 `[{text}]`**，与 ch5 `reference_strengths` 同构；用户点「引用」仅写入 `reference_talents`，点击「让教练汇总并建议关联」时后端将其与 step-1 领域合并去重作为 LLM 分析上下文（**不并入 `likes` 列表本身**，`linked_strengths` 由 LLM 在生成时按对应关系写入各项）。
- **运行**（/run）：LLM（`career_counselor`）生成 10–20 条 `likes`，每条 = {field, aspects[], linked_strengths[], sources[], locked}；`commentary` 含图 6-1 拆解建议。
- **契约要点**：
  - `locked=true` 项必须原样保留（`preserve_output` 透传，不重新生成）。
  - 不臆造领域；建议「领域→方面」拆解但不替用户定性；识别并提示合理性陷阱。
  - ch5 擅长之事经 `reference_talents` 传入，LLM 选 1–3 个最相关者写入对应项的 `linked_strengths`（子字段，随 `likes` 落库）。

### 4.3 抽屉 / 辅助面板（前端 UI，不进 config 级联）
- **100 例清单抽屉**：读 `ui_context.passion_examples`（id `p01`–`p100`，随 config 发布，前端读 config，不另接接口）；点击「引用」把 `text` 写入 Step 2 的 `passion_seeds`（领域 seed scratchpad，仅作分析上下文，不写入最终 `likes`）。
- **30 问抽屉**：权威源 `问题清单.md`，运行时由题库服务接入（回答存于 `book_notes`，前端按 `q_order` 取回；原型内置 demo 数组演示）。点击在 **Step 1** 追加回答，落入 step-1 的 `passion_questions`（与 q1–q5 并列作为 LLM 发现素材），**不进入 Step 2 直接引用**——其影响经 step-1 LLM 间接并入 `likes`（可在 `sources` 标记 `q{order}` 溯源），不成为独立下游键。
- **关联擅长之事面板**：读 `learner_profile.talents`（ch5 产出），点击加入 Step 2 的 `reference_talents`。

### 4.4 导师对话（mentor，贯穿）
- 上下文 = 已 `submitted` 的 step_runs 输出（step-1/step-2 结果）+ `mentor_hooks.references` 锚点（`talents`/`likes`，仅作开场回响与个性化追问）。
- 约束：导师只读 submitted 输出，绝不读草稿或未提交 LLM 结果；`talents`/`likes` 仅作导师钩子，绝不进入 step-1/step-2 的普通分析 Prompt（那两处的上下文由 `step_context`/`ui_context` 显式声明，当前均为 `[]` / 仅 passion_examples）；不替用户定性。

## 6. 各产出字段的锁定类型（lockable / readonly 契约）

| 字段 | 位置 | 类型 | 锁定/只读契约 |
|------|------|------|---------------|
| `likes` | step-1 / step-2 output | editable_list | **lockable**（按 item）；item 级 `locked` 阻止 LLM 覆盖/重排 |
| `likes[].field` | step-2 item | text | 用户可编辑 |
| `likes[].aspects` | step-2 item | editable_list | 用户可编辑（子列表） |
| `likes[].linked_strengths` | step-2 item | editable_list | 用户可编辑（子列表，来自 ch5） |
| `likes[].sources` | step-2 item | list | 自动（q1–q5 或 q61–q90 标记），readonly |
| `likes[].locked` | step-2 item | boolean | 用户锁定开关 |
| `commentary` | step-1 / step-2 output | markdown | **readonly**（LLM 映照点评，含合理性陷阱） |
| `reference_talents` | step-2 input | list_of_items | 用户 scratchpad，不锁；提交时作 LLM 上下文 |
| `passion_seeds` | step-2 input | list_of_items | 用户 scratchpad（来自 `ui_context.passion_examples` 的「引用」）；提交时与 `reference_talents`、step-1 领域合并去重作 LLM 上下文，**不写入最终 `likes`** |
| `q1..q5` | step-1 input | text | 用户输入，可编辑至 submitted 前 |

> 运行时锁定机制同 ch02/03/04/05：**整步提交态**由 `submitted` 控制（`edit_output` 在 submitted 态返回 409）；`lockable`/`readonly` 仅为 schema 意图声明（item 级 `locked` 由 `preserve_output` 透传保护）。勿再锚 legacy 内部 merge 逻辑。

## 8. 数据表与字段设计

### 8.1 持久化结论（新增 step_runs.stale 列，向后兼容迁移）
- 持久键 **`likes` 已在** `platform/backend/app/services/compaction.py` 的：
  - `PROFILE_FIELDS`（L16）
  - `STRUCTURED_FIELDS`（L34）
  - `MANDATORY_DOWNSTREAM_FIELDS`（L39）
  - → `likes` 本身**零新增表/列/迁移**，提交即自动并入 `learner_profiles.profile_json`；但为支持「上游重提交后使旧 step-2 结果过期」的隔离需求，需在既有 `step_runs` 表新增 `stale INTEGER NOT NULL DEFAULT 0` 列（详见 §8.4 迁移口径与 §8.7 失效规则）。
- `talents`（ch5，L17/34/39）已就绪，`reference_talents` 仅作 step-2 输入上下文，**不新增白名单键**。

### 8.2 逻辑落库形态（落于 `likes`）
```
likes: [
  {
    "field": "自我认知",
    "aspects": [{"text": "把复杂概念讲清楚"}, {"text": "帮助别人认识自己"}],
    "linked_strengths": [{"text": "善于用语言帮助别人"}],
    "sources": ["q1","q3"],
    "locked": false
  }
]
commentary: "<markdown 映照点评 + 合理性陷阱提醒>"
```

### 8.3 三路上下文（config 契约）
- `step_context: { references: [] }`（章节内级联走 step_runs；跨章不进步骤分析 prompt，与 ch03/04/05 同构）。
- `mentor_hooks`: `{ focus:"喜欢的事识别：内在兴趣 vs 外部有用性", references:["talents","likes"], entry_prompt:"…" }`（导师对话锚点，引用 ch5 擅长 + 本章 likes）。
- `ui_context`: `{ references: [], passion_examples: [...] }`（100 例清单数据源，随 active config 发布，前端直接读取已加载的 chapter config 即可，不另接接口；与 ch05 `strength_examples` 同路，仅展示用途，不进 LLM prompt）。

### 8.4 改动范围与契约测试（含 step_runs.stale 迁移）
- **有 schema 迁移**（与第三轮回复一致）：在既有 `step_runs` 表新增 `stale INTEGER NOT NULL DEFAULT 0` 列。迁移机制沿用项目既有约定（`app/db.py init_db()`）：在启动初始化时执行 `ALTER TABLE step_runs ADD COLUMN stale INTEGER NOT NULL DEFAULT 0`，并用 `try/except` 吞掉「重复列」报错以保证**幂等**（重复启动不报错）。旧库升级后不丢任何 `step_runs` 数据，旧行 `stale` 默认补 `0`。
- 其余改动：配置发布（reseed active config）、运行时上下文（`step_context` 声明 / `preserve_output` 透传给 steps/agent/assembler）、前端 renderer（结构化 `likes` 卡片渲染：领域/方面/关联擅长/来源/锁定 + 重新生成）、契约测试。
- **验收标准（同步开发侧第四轮 1.4）**：新库初始化后存在 `step_runs.stale` 默认 `0`；旧库升级不丢数据；重复执行启动迁移不报错；旧 run `stale` 默认 `0`；`status` 状态机不变；有迁移或数据库契约测试覆盖。

### 8.5 下游消费（ch07 / summary）
- ch07 取 `likes`（ch06）× `talents`（ch05），用 `work_purpose`（ch04）筛分「真正想做 / 作为兴趣」，`values`（ch04）作核心价值观，组合「想做的事」。四者均经 ch07 config `step_context`/`mentor_hooks.references=[talents,likes,work_purpose,values]` 契约注入。**ch7 不读 ch3、不消费 `importance`**（与 `context_requirements.py` 旧映射冲突，见开发侧待办）。消费方直接读 `learner_profile.likes`，兼容嵌套 `{field, aspects[], linked_strengths[], sources[], locked}` 结构。
- **summary（章节回顾）**：经 `run_summary()`→`load_profile()` 读取 `learner_profile`，以 `values`/`work_purpose` 作为章节摘要额外角度（`assembler.build_summary_prompt` 仅取此二者，实测 `agent.py:138`、`assembler.py:385-389`）；但 summary **不读取 `likes`、不消费 ch06 step-2 输出**，因此**不属于 ch06 `stale` likes 的消费方**，不为其增加 ch06 stale 门禁。若未来要基于用户 `likes` 做个性化摘要，须另开设计变更，不纳入本次 ch06 实施。summary 的「历史查看」仅针对章节摘要缓存，不展示 stale 的 ch06 step-2 结果。
- 修改 config 后需 **reseed** 覆盖旧草稿并消除 `check_config_consistency.py --chapter ch06` 的 DRIFT（参考 ch04/ch05 先例：config 变更后须 reseed）。

### 8.6 草稿持久化契约（前端 + 运行时，防 ch05 类遗漏）
- **草稿跨刷新/重新进入保留**：Step 1 逐题草稿（`q1–q5` + `passion_questions`）与 Step 2 引用草稿（`reference_talents`、`passion_seeds`、卡片编辑中内容）存于 `user_answers` / 草稿态 step_run，刷新或重新进入本章后原样恢复，并显示「上次保存于 {时间戳}」。`passion_questions` 的权威值由 questions 服务持有（book_notes），重新进入时前端重新按 q_order 取回以重建 step-1 草稿。
- **草稿与 submitted 隔离**：草稿仅承载于 `user_answers` / 既有的草稿态 step_run，与 `/run` 后的 `saved` 结果、`/submit` 的 `submitted` 正式结果明确隔离；草稿不可被下游 `references.from_exercise`、导师 `mentor_hooks` 或 compaction 读取。
- **保存失败明示**：自动保存或手动保存失败时，前端显示明确错误提示（非静默丢失），并保留本地可恢复内容。
- **不进下游/导师/profile**：草稿状态下的 `likes` 不进入 `learner_profile`、不被导师读取、不参与 ch07 组合。
- **回归测试要求**：刷新恢复、重新进入恢复、保存失败提示、submitted 后草稿不可污染下游，均须有契约测试覆盖。

### 8.7 上游重提交：stale 隔离与 learner_profile.likes 失效（权威口径）
> 对应开发侧第四轮问题 2。采用 **方案 B**（`learner_profile.likes = []`，不新增 profile 字段；旧值由 `step_runs` 中 `stale=1` 的历史 run 只读保留）。

- **触发条件**：仅当 ch06 **step-1 成功 `/submit`**（新 submitted run 写入）时触发；草稿 / `saved` / 重新 `/run` 不触发。
- **同一数据库事务内完成三动作**（任一失败整体回滚，杜绝「step-1 已新、step-2 已 stale、但 profile 仍旧 likes」的中间态）：
  1. 写入新的 step-1 `submitted` run；
  2. 将既有 step-2 的 `saved` / `submitted` runs 置 `stale=1`；
  3. 将 `learner_profile.likes` 置为 `[]`（当前值失效）。
- **新 step-2 提交前**：profile.likes 保持 `[]`，导师 / summary / ch07 均不得读取旧 likes（旧值仅在 `step_runs.stale=1` 历史中只读展示）。
- **新 step-2 提交成功**：由 §8.8 专属提交逻辑**显式选取「最新、非 stale」的 step-2 结构化 `likes`**覆盖写入当前 `learner_profile.likes`（不依赖通用 compaction 对同名 `likes` 的输出顺序合并）；若新 step-2 提交失败，profile 保持 `[]`（不恢复旧 likes）。
- **完成判定门禁（统一规则）**：`learner_profile.likes` 存在**且为非空数组**（`len(likes) > 0`）才视为第六章已完成；空数组 / 缺失均视为未完成。**ch07 进入前的上游门禁必须校验此规则**（防御性：即便 profile 清 `[]` 与 `step_runs.stale` 因代码路径分歧短暂不一致，ch07 也不消费过期 likes）。
- **读取优先级（统一）**：`step_runs` 取 `status='submitted' AND stale=0` 的最新 run；`learner_profile` 只读当前 `likes`；`stale=1` 历史 step-2 结果仅用于历史查看，不进导师 / summary / ch07 / compaction。
- **前端提示**：step-1 重提交后展示「你更新了第一步答案，第二步的旧分析已标记为历史记录，请重新运行并提交第二步。」

### 8.8 ch06 `likes` 写入规则（canonical，方案 A，权威契约）
> 对应开发侧第六轮问题 2。ch06 step-1 与 step-2 同名输出 `likes`，但语义不同，且**绝不允许通用 compaction 对两者做隐式合并**——通用 `_flatten_outputs`（`compaction.py:71-82`）按字段后者覆盖前者、且只读 `status='submitted'` 不筛 `stale=0`，会把 step-1 领域级 `likes` 与 step-2 结构化 `likes` 混合并污染 profile。故 ch06 采用**专属提交/compaction 规则（方案 A）**：

- **step-1 `likes`（领域级 `{text,locked,source}`）= 纯中间级联输入**：
  - 仅供 step-2 经 config `references.from_exercise: step-1` 读取；
  - **不进入 `learner_profile`、导师上下文（`mentor_hooks`）、summary、ch07**；
  - step-1 的 `/run`、保存草稿、`/submit` 均**不直接写入最终 profile.likes**；通用 compaction 不为 ch06 合并 step-1 的 `likes`。
- **step-2 `likes`（结构化 `{field,aspects[],linked_strengths[],sources[],locked}`）= profile 与 ch07 的唯一正式来源**：
  - 仅 step-2 成功 `/submit` 后，由**专属逻辑显式选取「最新、非 stale」的 step-2 结构化 `likes`**覆盖写入 `learner_profile.likes`；
  - step-2 的 `/run`、saved 结果**不写入** profile；
  - 不把 step-1 与 step-2 两个同名字段一起交给通用 compaction 再依赖输出顺序覆盖；
  - 其他允许字段（如 `commentary`，readonly）按现有通用规则处理。
- **step-1 重提交事务（与 §8.7 三动作一致）**：写新 step-1 run → 旧 step-2 `stale=1` → `profile.likes=[]`；**不把新的 step-1 likes 写回 profile**。
- **step-2 新提交成功**：用该次结构化输出**显式覆盖** profile.likes（= `len(likes) > 0` 视为完成）；若提交失败，profile 保持 `[]`（不恢复旧 likes）。
- **step-2 为空数组提交**：profile 写为 `[]`，统一视为 ch06 未完成；不得把中间领域 likes 写入 profile。

> 实施边界：方案 A 只影响 ch06 两级同名 `likes`，**不改变全局 `compact_profile` 语义**；其他章节仍走通用 compaction。ch06 的提交/compaction 钩子在写入 profile.likes 时绕过通用 `_flatten_outputs`，直接采用上述显式选取逻辑（详见 `待设计确认6_设计侧回复.md` §2）。
