## 2. 设计 ↔ 代码的核心断层（重构的真正工作量）

### 2.1 配置 schema 不兼容（最重要）
- 现有运行时契约：`{ steps: [ { step_id, user_input.questions, llm_op: { role_id, prompt_template(jinja2), output_schema } } ] }`
- 新设计契约：`{ chapter_id, exercises: [ { name, instruction, worksheet, user_action, llm_role, output_fields[], few_shot_examples[] } ], mentor_hooks, core_concepts, few_shot_examples }`
- **后果**：新 `chapter_config_chNN.json` 不能直接 `json.dumps` 灌入 `chapter_configs` 并被现有 `step_runner.py` / `steps.py` / 前端消费。两者必须二选一统一（见 §3.1）。

### 2.2 ch4 五步级联的跨步依赖在 `exercises` schema 中**无载体**
- 级联关系（来自 legacy `prompt_template` 与 handoff §7.4）：
  - step‑2 需要 step‑1 的 `top_values`
  - step‑3 需要 step‑2 的 `groups`
  - step‑4 需要 step‑2 的 `groups` + step‑3 的 `conversions`
  - step‑5 需要 step‑4 的 `ranked`
- legacy 用 jinja2 `{{ step_1.output.top_values }}` 注入；新设计（handoff §7.0）说"assembler 拼装、不提 jinja2"，但 `exercises` schema **没有 `references` / `depends_on` 字段**来声明"本步要注入哪些前序 exercise 的哪些 output_fields"。
- **结论（已解决，见 ADR-001 §2.2）**：`exercises[]` 现已增 `references: [{ from_exercise, fields }]`，`build_step_prompt` 据此从已 submitted 的前序 `step_runs.parsed_output` 注入。`chapter_config_ch04.json` 已作为 canonical 样例补完 5 步级联。`config_loader` 与 `agent.run_step` 须按此实现（M3）。

### 2.3 `output_fields` 缺渲染 / 类型元数据
- `exercises[].output_fields` 只是字符串数组（如 `["groups"]`）。
- 前端 `renderStepOutput`（index.html:1193）目前按**字段名硬编码分支**渲染：markdown / commentary+top_values / keywords(chip) / ranked(chip) / comments+improvements / work_purpose。**没有 `groups` / `conversions` 分支** → step‑2/3 输出会掉进最后的 `JSON.stringify` 裸 JSON 兜底（handoff §7.4 已标为阻塞项）。
- 更深层：前端无法从 `output_fields` 知道某字段该渲染成**可编辑 chip 列表**还是**纯 markdown 文本**，也不能知道是否 `readonly`（step‑4 的 `ranked` 是只读排序）。legacy 的 `output_schema.fields[].{type, readonly, lockable}` 提供了这点，新 schema 丢了。
- **结论（已解决，见 ADR-001 §2.3）**：`output_fields` 升级为 `oneOf` 字符串|对象，对象含 `type`/`readonly`/`lockable`（`type` 枚举 markdown/text/editable_list/list/number/select/json/table）。向后兼容字符串写法（等价于 `{name, type:unknown}`），现有 ch01‑03/ch05‑08 配置暂无需改写，M0 由 coding agent 批量转对象。`chapter_config_ch04.json` 已转换为类型化样例。前端须据 `type` 分支渲染并补 `groups`/`conversions` 两分支（M4）。

### 2.4 `learner_profiles` / `conversation_summaries` 表未建
- `db.py` 的 `SCHEMA` 里**没有**这两张表；`config_loader.load_profile()` 用 `try/except` 容错（表不存在返回 `{}`）。
- M1 必须真正建表 + 写 compaction 服务（handoff §6）。

### 2.5 step 装配器未实现
- `app/runtime/agent.py` 只有 `run_mentor` / `run_summary`；`run_step` 是 `TODO` 注释。
- `assembler.py` 只有 `build_mentor_prompt` / `build_summary_prompt`，没有 `build_step_prompt`。
- M3 必须补 `build_step_prompt`（persona + instruction + worksheet + few_shot + 前序注入）并把 `step_runner` 接线到 `agent.run_step`。

### 2.6 chapter_id 双标识
- 新配置 `ch04` vs legacy `04-important`。`book.py` 已有别名兼容，但属于"双轨"。须做一次迁移（§3.4），否则 `learner_profiles.mentor_hooks.references` 与既有 `step_runs` 跨章引用会混乱。

### 2.7 前端非 Next.js、且不被后端托管
- 真实前端是单 `index.html`，前端逻辑全在 `<script>` 内（约 700+ 行 JS）。
- `API` 硬编码 `http://localhost:8011`，后端 `main.py` 未挂静态目录。
- 影响：M4/M5 的前端改动都在这一文件内做"原地增强"，且需明确"怎么跑起来"。

### 2.8 用户身份缺失
- 全站单用户本地部署，无 auth。`learner_profiles` 以 `user_id` 为主键，但**没有谁传 user_id**：`agent.run_mentor(chapter_id, user_id, ...)` 的 `user_id` 目前无来源。
- 须约定一个常量（如 `"local"`）作为当前单用户标识（§3.5），schema 仍保留 `user_id` 以便将来多用户。

## 3. 架构决策（原 7 项待拍板，已全部拍板 — 详见 ADR-001）

### ★ 3.1 运行时配置契约（已拍板：**Option B — exercises 原生**）
- **Option A（seed 期转译，运行时小改）**：保留 legacy `steps/llm_op` + jinja2 作为运行时契约；写一个 `chapter_config_chNN.json → legacy steps` 的转换器，把 `exercises` 的 instruction/few_shot 编进 `prompt_template`，把 `output_fields` 编成 `output_schema`。step_runner / 前端几乎不动，只补 ch1–3 / ch5–8 的 seed。
  - 优点：改动小、风险低、前端不动。
  - 缺点：**未真正实现"配置驱动 assembler"**（handoff §3.1 的核心）；few_shot 靠拼字符串进 jinja2，脆弱；mentor_hooks 仍须单独从 config 取。
- **Option B（exercises 原生，运行时重写）**：以 `exercises[]` 为运行时契约；重写 `step_runner` 用 `build_step_prompt`（persona + instruction + worksheet + few_shot + 前序输出注入），去掉 jinja2；前端 `renderStepBody` / `renderStepOutput` 改为读 `exercises[].output_fields` + 类型元数据。
  - 优点：干净、完全配置驱动、真正落实 ≤3k assembler、与 handoff §7.0 一致。
  - 缺点：blast radius 大（step_runner 重写 + 前端 step 渲染器重写 + 补 groups/conversions）。
- **✅ 已拍板：选 B。** 以 `exercises[]` 为运行时契约，重写 `step_runner` 走 `build_step_prompt`，彻底去掉 jinja2；前端 `renderStepBody`/`renderStepOutput` 读 `exercises[].output_fields` + 类型元数据。放弃 Option A（seed 转译保留 jinja2）。理由：落实"配置驱动、不写死 prompt"主旨，且必须连同 3.2/3.3 一起做（现已同步落地 schema + ch04）。详见 ADR-001 §2.1。

### ★ 3.2 跨步引用机制（已拍板：`exercises[].references`）
- **✅ 已拍板**：`exercises[]` 每项增 `references: [{ from_exercise: "step-1", fields: ["top_values"] }]`（省略 `fields` 即注入该步全部 output）。`build_step_prompt` 据此从同章已 `submitted` 的 `step_runs.parsed_output` 取前序字段注入 user prompt。ch4 级联已被 `chapter_config_ch04.json` 完整表达，且受 ≤3k 护栏约束（仅按需注入、不全量）。详见 ADR-001 §2.2。

### ★ 3.3 output 字段渲染 / 类型元数据（已拍板：类型化 oneOf）
- **✅ 已拍板**：`output_fields` 升级为 `oneOf` 字符串|对象，对象含 `name`/`type`/`readonly`/`lockable`；`type` 枚举 `markdown|text|editable_list|list|number|select|json|table`。向后兼容字符串写法（等价 `{name,type:unknown}`），现有 ch01‑03/ch05‑08 配置暂不改，M0 由 coding agent 批量转对象。前端 `renderStepOutput` 据 `type` 分支：`editable_list` → 可编辑 chip（带 readonly/lockable）；`list` → 只读 chip；`markdown` → 直接渲染；并**补 `groups` / `conversions` 两个分支**（groups=umbrella+keywords 卡片组，conversions=原值→转化值+why_chain 列表），同时修复 handoff §7.4 阻塞项。`chapter_config_ch04.json` 已转类型化样例。详见 ADR-001 §2.3。

### 3.4 chapter_id 迁移策略（已拍板：统一 `ch0N`）
- **✅ 已拍板**：统一规范为 `ch01..ch08`；做一次一次性迁移脚本 `migrate_chapter_ids.py`：将 `step_runs` / `chapter_configs` / `chapter_chat` / `chapter_summaries` 的 `04-important` → `ch04`，随后从 `book.py` 删除 `CH_ID_ALIAS`。旧 `seed_ch4.py` 弃用，改用统一 `seed_chapters.py`。
- 风险：若有用户数据，迁移前必须备份 `ww.db`。

### 3.5 user_id 策略（已拍板：常量 `local`）
- **✅ 已拍板**：当前单用户，常量 `DEFAULT_USER_ID = "local"`；`config_loader.load_profile/save_profile`、`agent.run_mentor/run_summary/run_step` 默认取该值（前端无需改）。schema 保留 `user_id` 主键以便将来。

### 3.6 前端托管 / 运行方式（已拍板：后端挂静态，方案 a）
- **✅ 已拍板（方案 a）**：后端 `main.py` 用 `StaticFiles` 挂载 `frontend/index.html` 到 `:8011/`，前后端同端口同源，消除硬编码 `http://localhost:8011` 跨域问题；前端 `API` 改相对路径 `/api`。选 a 而非 b 的理由：单站点部署更干净，且一次性消除硬编码端口。

### 3.7 `conversation_summaries` 是否实现（已拍板：建表延迟实现）
- 设计有（handoff §6.1），但 `config_loader` 未引用、`chat.py` 未用。属于"长程对话超 sliding window 后的回填摘要"，属增强项。
- **✅ 已拍板**：M1 建表（成本极低），**实现延迟到 M5 之后**作为可选增强；M3 的 mentor 先用 `build_mentor_prompt` 的截历史兜底。

## 8. 给 Coding Agent 的"防跑偏"红线（继承 handoff §11）

- 角色 system prompt → 一律从 `PRD-chN §3.1` + `config/*` 取，**不要自己写**。
- 章节知识 → 按 `assembler` 切片注入，**不要全量喂 MD**。
- 跨步依赖 → 用 `exercises[].references` 声明 + `build_step_prompt` 注入，**不要写 jinja2 `{{ }}`**（M0 后 legacy 模板作废）。
- 字段名/类型 → 必须匹配 `chapter_config.output_fields` + §3.3 元数据，**不要发明**。
- 跨章记忆 → 只读 `learner_profiles` 压缩档案，**不要读原始八章 step_runs**。
- 配置 → 运行时读 DB，**不要硬加载 JSON 文件**。
- 任何改动先保留旧路由可回滚，再灰度切换。
