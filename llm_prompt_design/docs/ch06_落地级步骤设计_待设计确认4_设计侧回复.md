## 问题 1：数据库迁移规则与落地文档冲突 —— 确认采用修订口径

### 1.1 修订口径：采纳
> ch06 不新增业务表，也不新增 `likes` 专用表；但为支持上游重提交后的过期隔离，在既有 `step_runs` 表新增 `stale INTEGER NOT NULL DEFAULT 0` 列，并执行一次向后兼容的 SQLite 迁移。`referenced_outputs` 继续复用既有 JSON 字段保存依赖指纹。

落地文档 §0 / §8.1 / §8.4 原「零新建数据库表/列/迁移」「无 schema 迁移」表述已全部改为上述口径。**冲突已消除，config 仍是运行时唯一权威，新增的 `stale` 列属于数据库实施层、不进 config 字段契约，二者不矛盾。**

### 1.2 四项迁移要求（以项目既有约定为准，已实测 `app/db.py`）
- **Q1 启动补列 vs 独立脚本**：采用**启动初始化自动补列**，与项目既有机制一致——`init_db()`（`app/db.py:179`）已对 `step_runs` 用 `ALTER TABLE step_runs ADD COLUMN error TEXT`（L186）做升级补列。本次只需在同处追加一条 `ALTER TABLE step_runs ADD COLUMN stale INTEGER NOT NULL DEFAULT 0`。
- **Q2 是否幂等**：**必须幂等**。既有代码已用 `try/except Exception: pass`（L187-191）吞掉「重复列」报错。新增列沿用同一包裹即可，重复启动不报错。
- **Q3 旧数据默认值**：统一 `DEFAULT 0`，旧 run 补列后 `stale` 自动为 `0`（未重提交过的历史结果视为有效，符合预期）。
- **Q4 旧查询/插入兼容**：新增列带 `NOT NULL DEFAULT 0`，旧代码不感知该列也能正常读写（列存在且恒有值）；新查询按 `stale=0` 过滤即可。无破坏。

### 1.3 验收标准：采纳开发侧 1.4（略，已写入落地文档 §8.4）

## 问题 2：learner_profile.likes 失效方式与事务边界 —— 确认方案 B

### 2.1 采用方案 B（profile.likes = []，不新增 profile 字段）
理由：单一当前值来源（`learner_profile.likes`），导师 / summary / ch07 只认这一个键，避免方案 C 的 `likes_status` 双重状态源、方案 D 的 `likes_history` 契约膨胀、方案 A 的「键缺失 vs 值空」歧义。旧值由 `step_runs.stale=1` 历史 run 只读保留，历史可追溯。

### 2.2 事务与恢复语义（全部确认开发侧建议）
1. step-1 重提交时，以下三动作**必须在同一数据库事务**完成：写新 step-1 submitted run → 既有 step-2 `saved/submitted` 置 `stale=1` → `learner_profile.likes` 置 `[]`。
2. 任一动作失败**整体回滚**，杜绝「step-1 已新 / step-2 已 stale / profile 仍旧 likes」中间态。
3. 新 step-2 提交失败时，profile **保持 `[]`**，不恢复旧 likes，直到新 step-2 成功提交覆盖。
4. **仅 step-1 成功 `/submit` 触发**；草稿 / `saved` / 重新 `/run` 不触发。
5. 页面提示文案采纳：「你更新了第一步答案，第二步的旧分析已标记为历史记录，请重新运行并提交第二步。」

### 2.3 读取优先级（确认）
- `step_runs`：`status='submitted' AND stale=0`，取最新 run；
- `learner_profile`：只读当前 `likes`，空值 / 缺失均视为第六章未完成；
- `stale=1` 历史 step-2 结果：仅历史查看，不进导师 / summary / ch07 / compaction；
- 新 step-2 成功提交后由其覆盖写入当前 `learner_profile.likes`。

## 设计侧主动补充的两点（请开发侧一并落实，非阻塞）

### 补充 A：完成判定门禁必须改为 `len(likes) > 0`
方案 B 下 `profile.likes` 键**始终存在**（可能为空数组）。原有「`likes` 键存在即视为 ch06 完成」的判定（如 `test_context_integrity.py`、`test_ch03_contract.py` 等处的 `in profile` 风格判定）会误判空数组为已完成。**统一门禁规则：`learner_profile.likes` 存在且为非空数组才视为完成。** 该门禁须应用于 mentor、summary、ch07 上游校验三处。

### 补充 B：ch07 上游门禁做防御性双校验（防两态漂移）
`step_runs.stale` 与 `profile.likes=[]` 是两套鲜度表达，正常由同一事务保持同步；但若代码路径分歧（如并发、补列迁移边界）可能短暂不一致。建议在 ch07 进入前的上游校验**同时**校验：① `learner_profile.likes` 非空；② ch06 step-2 存在 `status='submitted' AND stale=0` 的 run。二者任一不满足即阻断 ch07，避免消费过期 likes。

> 注：因 compaction 是「合并现有 profile + 新章 output」（`steps.py:501` `compact_profile([existing_profile, *outputs])`），若 profile.likes 被清为 `[]` 后进入后续章 submit，空数组在 `_flatten_outputs` 会被跳过（`[]` 属排除值），最终 likes 键可能「消失」而非保留为 `[]`——对门禁而言「缺失」与「空数组」等价（均=未完成），无功能影响；仅提示开发侧：清 `[]` 态不一定能被后续 compaction 读回为 `[]`，读取方应同时兼容「键缺失」与「空数组」两种未完成形态。
