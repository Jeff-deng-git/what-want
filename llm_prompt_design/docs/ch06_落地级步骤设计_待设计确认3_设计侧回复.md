## 1. Q1：q1–q5 与 `passion_questions` 的必填关系 —— 设计侧拍板（方案 A）

### 1.1 决策
**q1–q5 继续全部必填（`required: true`），30 问 `passion_questions` 保持 `required: false`（可选补充）。config 当前形态即最终结论，不改。**

### 1.2 澄清「误读」来源
第二轮回复 §1.2 原文：
> 「若放 step-2，则『只用 30 问、跳过 5 问』的用户会得到空 step-1 输出 → step-2 无内容可结构化，流程断裂；放 step-1 则更鲁棒。」

这句话论证的是 **30 问的「所属步骤」选择（step-1 优于 step-2）**，其前提是 **q1–q5 始终是强制主路径**——正因 q1–q5 必填，「只用 30 问而跳过 5 问」本就是被禁止的状态，故「放 step-1 更鲁棒」是指「即便用户 heavily 使用 30 问，也仍处在 step-1 框架内参与发现」，并非「允许跳过 5 问」。开发侧据此认为存在矛盾，实为措辞歧义。

### 1.3 明确规则
- q1–q5 是本章**强制主流程**五问，必须全部填写才能运行 step-1；
- 30 问是**严格追加素材**，不能替代 q1–q5；
- UI 文案建议：「先回答五个问题；若素材仍不足，再打开『热情 30 问』补充」。

### 1.4 方案 B 的子问题（因采纳 A，均不适用，记录备查）
1. 至少一条证据判定：不适用（q1–q5 各自必填已保证证据存在）。
2. 空答案/纯空格/只存题未答：视为该 q 未完成，阻塞 step-1 运行。
3. 运行后删空所有 q1–q5 只留 30 问：不允许——q1–q5 必填校验在每次 /run 前生效，删空即无法重跑，提示「请补全五个问题」。

> 结论：开发侧倾向的方案 A 与设计口径一致，采纳；无需新增「至少一条证据」的运行时校验分支。

## 2. Q2：「已过期」结果的状态表示与下游隔离 —— 设计侧拍板（方案 B）

### 2.1 决策
**采纳方案 B：不新增 `expired` 通用状态，新增 `stale` 独立布尔列 + 依赖指纹。**

- **`stale` 存储落点（设计侧指定）**：在 `step_runs` 表**新增 `stale INTEGER DEFAULT 0` 列**（一次迁移；这是独立布尔列，**不是**对 `status` CHECK 枚举的扩展，不触碰 `draft/saved/submitted/failed` 通用状态机，符合开发侧 §4 当前动作约束）。
- **依赖指纹存储落点**：存于 `referenced_outputs` JSON，新增键：
  ```json
  {
    "source_step_id": "step-1",
    "source_run_id": "<step-1 submitted run id>",
    "source_submitted_at": "<timestamp>"
  }
  ```
  （`referenced_outputs` 本就记录本步消费的上游，放此处语义最贴合；`user_answers` 是用户输入、`parsed_output` 是结果，均不合适。）

### 2.2 下游隔离规则（确认开发侧建议）
1. **step-1 新提交后，旧 step-2 `likes` 立即从 `learner_profile` 失效**：compaction 已写入 `learner_profile.likes` 的，应在 step-1 重提交时清除/标记不可用，直到新的 step-2 提交完成才重新写入。
2. **导师暂不能读旧 likes**：mentor 读取 `likes` 时须 `stale=0`，旧结果在 step-2 重跑前对导师不可见。
3. **ch07 视 stale 为上游未就绪**：ch07 经 `mentor_hooks.references=["talents","likes"]` / `step_context` 读 ch06 `likes` 时，若命中 `stale=1` 的 step-2 结果，应按「上游未就绪」处理（与缺失同逻辑：阻断/提示「请先完成第六章」），不得消费过期 `likes`。
4. **只选「最新且未过期」**：mentor、`learner_profile` compaction、ch07 三处读取路径，必须筛选 `stale=0` 且为最新 `submitted` 的 step-2 run。

### 2.3 重跑语义
- step-1 重新 `submitted` → 既有 step-2 `saved`/`submitted` 标记 `stale=1`，旧结果显示为只读历史（可查看，不进下游）；
- 用户重跑 step-2 成功提交后，新 run `stale=0` 且 `referenced_outputs` 指向最新 step-1 run，旧 `stale=1` run 退为历史；
- 不允许 `stale=1` 的 step-2 结果作为导师/ch07/profile 输入（见 §2.2）。

## 3. Q3：`sources` 来源范围、格式与字段说明 —— 设计侧拍板（全量统一）

### 3.1 决策（确认开发侧建议）
1. **允许混合**：`sources` 可同时含 q1–q5（`q1`…`q5`）与 30 问（`q61`…`q90`）。
2. **统一格式**：固定小写 `q` + 全局题库序号，如 `q61`；不使用 `61`、`热情-1`、题目文本。
3. **单值 vs 数组**：step-1 输出单值 `source`（string）保持现有；step-2 输出数组 `sources`（list）；某领域来自多题时由 step-2 归并为数组，step-1 不输出数组。
4. **不可溯源时**：返回**空数组 `[]`**，绝不猜测/编造来源。
5. **UI 显示**：数据层必须保留（`sources` 进 `likes` 持久化）；**UI 显示可选**——建议卡片上以淡标签展示来源号（如 `q61`），便于用户回溯，但非强制验收项。

### 3.2 已落盘的设计侧改动（config 标签）
- step-1 `likes.item.source` label：`来源` → **`来源（q1–q5 或 q61–q90；小写 q+全局题号）`**。
- step-2 `likes.item.sources` label：`来源（Q1–Q5）` → **`来源（q1–q5 或 q61–q90；小写 q+全局题号；无法可靠溯源时留空数组）`**。
- 上述两处已写入权威 config 并通过 Draft7 校验。
