## 1. 已权威拍板、可直接落地的项（附出处）

1. **exercise = step（一对一）**：`exercises[]` 每个元素就是一个前端 step 区块。`chapter_config_ch05/06/08.json` 均只有 `exercises[0]`，即每章**恰好 1 个正式 step**（§7.0；schema L113）。
2. **顶层 output 字段名与类型（不可改名、不可加名）**：
   - ch05：`talents`（editable_list，lockable=true）
   - ch06：`likes`（editable_list，lockable=true）
   - ch08：`success_statement`（text，lockable=true）、`color_bath_log`（table）
   - 依据：三份 canonical config + schema `output_fields` 类型枚举 + §7.9 防跑偏。
3. **旧 PRD 字段名作废**：`strengths`/`passions`/`true_calling`/`purpose_statement`/`success_manifesto` 等一律以 canonical 名为准；开发侧回写 PRD 时统一对齐（§7.9、§6.2）。
4. **跨章读取只用 `mentor_hooks.references` + `learner_profiles`**；章节内级联只用 `exercises[].references` → 前序 `step_runs.parsed_output`。**两机制勿混**（§7.0、§1.4 评审纠错）。
5. **profile 键集合固定（§6.2）**：`likes/talents/intersection/success_statement/values/work_purpose/ranked/formula/importance/misconceptions_cleared/external_voices/internal_external_ratio/reclaim_item/current_chapter/open_questions/milestones`。**新增键（如 color_bath_log）需设计侧拍板**，不能自行加。
6. **lockable 语义区分（重要，避免误用）**：ch05 `talents` / ch06 `likes` / ch08 `success_statement` 用 `lockable=true` 是**正确**的——这些是「用户可编辑 + 可选锁定」的列表/文本。这与 ch03 `intersection` 改 `readonly` 不冲突：`intersection` 是 LLM-output-only（用户不手填），才用 readonly；talents/likes 是用户编辑产出，应用 lockable。**请勿把 ch03 的 readonly 处理套到 ch05/06/08。**
7. **下游只读取已 `submitted` 的 run**：未提交 = 不可作为正式上下文，缺失则需阻断并返回上下文错误（§3.1「声明的前序 submitted 输出」+ §14「缺失来源或字段时阻止生成」）。开发侧建议的"未提交=不可作为正式上下文"确认采纳。
8. **ch05/ch06 step 不读上游 work_purpose/talents**：两份 config 的 exercise 均**无 `references` 字段**，按 §3.1 其 step prompt 仅注入「用户答案 + 本章 MD 切片 + 本章 few_shot」。`work_purpose`/`talents` 仅通过 `mentor_hooks.references` 供导师上下文，不进 step LLM。这是当前 canonical 的既定形态，不是遗漏（除非设计侧后续显式加 step 级跨章注入）。
9. **ch08 success_statement = 单文本（text）**：结构化 `success_manifesto`（non_negotiables/byproducts）不在 canonical，已收敛（§7.9 + `chapter_config_ch08.json`）。

## 2. 待设计侧补充拍板的缺口（G1–G9，开发侧不应自行推进）

- **G1 — editable_list 的 item 级 schema 未定义**：schema 只把 `editable_list` 描述为"可编辑 chip"，未定义 item 内部结构。dev 文档 §2.3 提议的 `id/evidence/source_refs/locked` 目前**无任何权威定义**。需设计侧拍板：item 是否用对象（含 id/evidence/source_refs/locked），还是先用纯字符串列表（最简）。
- **G2 — ch05/06/08 结构化输入（input_schema）未声明**：schema 虽已支持 `input_schema`（text/list_of_items/checklist/select/radio），但三份 canonical config 的 exercise **均未声明 `input_schema`**，仍用 `worksheet`/`instruction` 自由文字描述输入（ch05 八角度、ch06 1–2 件拆解）。前端如何渲染"8 格""拆解元素"当前无契约。需设计侧拍板是否补 `input_schema`（如 ch05 用 checklist 风格 8 项、ch06 用 list_of_items）。
- **G3 — ch08 未接入 ch07.intersection（机制缺口）**：ch08 练习前提是"记录与『想做的事』相关的信号"，而"想做的事"= ch07 `intersection`。但 canonical `chapter_config_ch08.json` 的 exercise **无 `references`**、`mentor_hooks.references=[values, work_purpose, talents, likes]` 也**不含 intersection**。即当前 canonical 既未让 step 也未让 mentor 引用 intersection。需设计侧拍板：① 是否把 `intersection` 加入 ch08 `mentor_hooks.references`；② step 是否需要系统注入 intersection 作观察锚点（当前 §3.1 的 step 输入模型**不含跨章 profile 注入**，若需则属机制扩展，须单独设计）。
- **G4 — color_bath_log 是否进 profile 未定**：§6.2 profile 键**不含 color_bath_log**，且 ch08 `mentor_hooks.references` 也未列它。即 7 天记录只落在 `step_runs`，导师无法引用历史色彩浴。需设计侧拍板：color_bath_log 是否加入 profile 键（加则导师可读）；否则接受"仅 step_runs、导师不引用"。
- **G5 — ch08 依赖 gate 逻辑未显式定义**：§7.7 明确定义了 ch07 的 gate（缺 ch3/ch4 整章锁定），但 §7.8 未对 ch08 写 gate。ch08 上游含 ch07.intersection（核心锚点）、ch04 values/work_purpose、ch05 talents、ch06 likes。需设计侧拍板：哪些为硬 gate（缺则整章锁定，建议至少 ch07.intersection 已提交）、哪些为软依赖（导师综合上下文，缺则提示不阻断）。
- **G6 — ch06 合理性陷阱（trap_warnings/confidence）取舍**：旧 PRD 有该机制，canonical `chapter_config_ch06.json` 无对应 output_fields（§7.9 不新增字段）。需设计侧拍板：本期是否实现（若实现须先定义字段名/类型并加进 config）、还是进 backlog。
- **G7 — ch08 实现手段 / 海胆转化取舍**：canonical 已收敛出范围（§0 冲突 4）。需设计侧拍板：确认"本期不实现"，还是作为 backlog 后续补（若补须先定义 step/字段并扩展 config）。
- **G8 — success_statement 生成时机与展示字段**：canonical 仅定"text + lockable"。何时生成（7 天完成后 vs 允许中途草稿）、是否需姓名/日期/导出图等展示字段是否进后端 schema，权威文档未定。需设计侧拍板（建议：7 天提交后由 LLM 归纳生成、用户编辑锁定；展示字段不进后端 schema，前端派生即可）。
- **G9 — 运行/编辑/锁定/提交状态机细化**：权威文档只定了"submitted 才进下游""locked 项不被覆盖"（§3.1/§7.0/§14）。详细状态（草稿/已运行/已提交/新版本）属实现细节，但必须守住上述硬规则。建议实现时以"lockable 项永远保留、unlocked 项重跑可被覆盖、下游只读最后 submitted run"为准。
