## 1. 开发侧问题 1：summary 可读取 profile，但不应消费 stale 的 ch06 likes

### 1.1 采纳统一口径

> 当前 summary 可以读取 `values`/`work_purpose` 作为章节摘要的额外角度，但不读取 `likes`，因此不属于 ch06 stale likes 的消费方。除非未来设计新增基于用户 likes 的个性化摘要，否则不为 summary 增加 ch06 stale 门禁。

### 1.2 四项确认

1. **保留** summary 对 `values`/`work_purpose` 的额外角度注入 → 确认保留（实测 `assembler.py:385-389` 即此行为，符合设计）。
2. **明确禁止注入 `likes`/`talents`/其他 ch06 step-2 输出** → 确认：`build_summary_prompt` 仅取 `profile.values` 或 `profile.work_purpose`，不触碰 `likes`/`talents`/step-2 输出。建议开发侧在代码层显式约束「不读取 `likes` 键」，以防未来误加。
3. **后续若 summary 需消费 `likes`，须另开设计变更** → 确认，不纳入本次 ch06 实施。
4. **summary「历史查看」仅针对章节摘要缓存，不展示 stale 的 ch06 step-2 结果** → 确认：`conversation_summaries` 为导师聊天历史，与用户 step-2 输出无关；summary 不消费 `likes`，自然不会展示 stale 的 ch06 step-2 结果。

### 1.3 第五轮回复 §4 误述勘误（重要）

第五轮回复 §4 称「summary 不引用 `likes`/`profile_json`/`load_profile`（grep 零匹配）」——**该论据错误**：当时 grep 了不存在的 `app/routers/summary.py` 路径，而真实逻辑在 `agent.py:138`（`run_summary` 调用 `load_profile`）与 `assembler.py:385-389`（`build_summary_prompt` 读 `values`/`work_purpose`）。结论方向（不增加 ch06 stale 门禁）仍成立，但支撑论据已在该回复文档中加 ⚠️ 勘误更正。本回复 §1.1/§1.2 为最终权威口径。

## 2. 开发侧问题 2：ch06 step-1 与 step-2 同名 likes 的 canonical 写入规则

### 2.1 采纳唯一口径

> ch06 step-1 的 `likes` 只作为 step-2 的章节内级联输入，不进入 `learner_profile`、导师上下文、summary 或 ch07。只有 ch06 step-2 成功 `/submit` 后的结构化 `likes`，才可以写入当前 `learner_profile.likes`，并作为 ch07 的正式 likes 输入。

### 2.2 五项确认

1. step-1 的 `/run`、保存草稿、`/submit` 均**不直接写入**最终 profile `likes` → 确认。
2. step-2 的 `/run` 和 `saved` 结果也**不写入**最终 profile，只有成功 `/submit` 才写入 → 确认。
3. step-2 `likes` 为空数组时，profile 保持/写为 `[]`，统一视为 ch06 未完成（`len(likes) > 0` 门禁）→ 确认。
4. step-1 重新 `/submit` 时：旧 step-2 `stale=1` 且 `profile.likes=[]`，且**不把新的 step-1 likes 写回 profile** → 确认（与 §8.7 三动作一致）。
5. step-2 新提交成功时，用该次结构化输出**显式覆盖** profile `likes`，而非把 step-1 与 step-2 两个同名字段交给通用 compaction 再依赖输出顺序覆盖 → 确认。

### 2.3 通用 compaction 与 ch06 专属规则的边界：采纳方案 A

- 通用 `compact_profile` / `_flatten_outputs`（`compaction.py:71-82`）继续服务其他章节；
- ch06 step-1 submit：只执行 stale 标记（旧 step-2 `stale=1`）+ `profile.likes=[]`，**不执行** likes 写入、不触发通用 compaction 合并；
- ch06 step-2 submit：专属逻辑**显式选取「最新、非 stale」的 step-2 结构化 `likes`** 覆盖写入 `profile.likes`，绕过通用 `_flatten_outputs` 对同名 `likes` 的隐式合并；
- ch06 step-1/step-2 的其他允许字段（如 `commentary`，readonly）按现有通用规则处理；
- 方案 A **只影响 ch06 两级同名 `likes`，不改变全局 compaction 语义**，其他章节回归风险最低（开发侧建议正确，采纳）。

### 2.4 验收用例（来自 2.4，方案 A + §8.7 已覆盖）
