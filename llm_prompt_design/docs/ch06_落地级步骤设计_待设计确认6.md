## 1. summary 可读取 profile，但不应消费 stale 的 ch06 likes

### 1.1 设计侧回复与实际代码的差异

第五轮回复称 summary：

> 不引用 `likes` / `profile_json` / `load_profile`。

但当前运行时代码实际存在 profile 读取：

- `platform/backend/app/runtime/agent.py:138`：`run_summary()` 调用 `load_profile(user_id)`；
- `platform/backend/app/runtime/agent.py:139`：将 profile 传给 `build_summary_prompt()`；
- `platform/backend/app/runtime/assembler.py:381-389`：`build_summary_prompt()` 会读取 profile 中的 `values` 或 `work_purpose`，作为摘要的额外角度。

当前核对结果是：

- summary 会读取 profile 中的 `values/work_purpose`；
- summary 当前没有读取 profile 中的 `likes`；
- 因此 ch06 stale likes 不会进入当前 summary Prompt；
- 书籍章节摘要与用户 ch06 likes 的 freshness 目前是解耦的。

### 1.2 请设计侧确认的唯一口径

请确认并将相关回复文字统一为：

> 当前 summary 可以读取 `values/work_purpose` 作为章节摘要的额外角度，但不读取 `likes`，因此不属于 ch06 stale likes 的消费方。除非未来设计新增基于用户 likes 的个性化摘要，否则不为 summary 增加 ch06 stale 门禁。

同时请确认：

1. 是否保留当前 summary 对 `values/work_purpose` 的额外角度注入；
2. 当前 summary 是否明确禁止注入 `likes`、`talents` 及其他 ch06 step-2 输出；
3. 后续如果 summary 需要消费 `likes`，是否必须另开设计变更，不纳入本次 ch06 实施；
4. summary 的“历史查看”是否仍只针对章节摘要缓存，不展示 stale 的 ch06 step-2 结果。

开发侧建议保留现有 `values/work_purpose` 行为，并仅在文档中修正“summary 完全不读取 profile”的表述，避免误导开发实施。

## 2. ch06 step-1 与 step-2 同名 likes 的 canonical 写入规则

### 2.1 当前字段形态

ch06 两个步骤都使用输出键 `likes`，但语义不同：

- **step-1**：领域级中间发现结果：

```json
{
  "likes": [
    {"text": "领域", "locked": false, "source": "q1"}
  ],
  "commentary": "..."
}
```

- **step-2**：最终结构化结果：

```json
{
  "likes": [
    {
      "field": "领域",
      "aspects": [{"text": "喜欢的方面"}],
      "linked_strengths": [{"text": "关联的擅长之事"}],
      "sources": ["q1"],
      "locked": false
    }
  ],
  "commentary": "..."
}
```

第五轮回复已经确认：

- ch06 step-2 是 ch07 当前 `likes` 的正式来源；
- ch03 的旧 likes 不再作为 ch07 正式输入；
- ch06 step-1 是 step-2 的中间发现阶段。

但还需要将“中间结果不得进入 profile、最终结果唯一写入 profile”的规则写成明确的运行时契约。

### 2.2 请设计侧确认以下 canonical 规则

请确认是否采用以下唯一口径：

> ch06 step-1 的 `likes` 只作为 step-2 的章节内级联输入，不进入 `learner_profile`、导师上下文、summary 或 ch07。只有 ch06 step-2 成功 `/submit` 后的结构化 `likes`，才可以写入当前 `learner_profile.likes`，并作为 ch07 的正式 likes 输入。

请进一步确认：

1. step-1 的 `/run`、保存草稿、`/submit` 均不直接写入最终 profile `likes`；
2. step-2 的 `/run` 和 `saved` 结果也不写入最终 profile，只有成功 `/submit` 才写入；
3. step-2 `likes` 为空数组时，profile 是否保持/写为 `[]`，并统一视为 ch06 未完成；
4. step-1 重新 `/submit` 时，是否执行：旧 step-2 `saved/submitted` → `stale=1`，同时 profile `likes=[]`，且不把新的 step-1 likes 写回 profile；
5. step-2 新提交成功时，是否用该次结构化输出**显式覆盖** profile `likes`，而不是把 step-1 与 step-2 两个同名字段一起交给通用 compaction 再依赖输出顺序覆盖。

### 2.3 通用 compaction 与 ch06 专属规则的边界

当前 `platform/backend/app/routers/steps.py` 的 `_maybe_compact()` 是通用章节逻辑，会读取章节内各 step 的 submitted 输出并调用 `compact_profile()`。由于 ch06 step-1 与 step-2 都有 `likes`，如果不增加明确优先级，可能出现：

- step-1 的领域级 likes 覆盖 step-2 的结构化 likes；
- step-2 的结构化 likes 覆盖顺序依赖数据库查询顺序；
- stale 的旧 step-2 被再次选中并写回 profile；
- step-1 提交后 compaction 又把中间 likes 写回 profile，抵消 `likes=[]` 的失效动作。

请设计侧确认开发实现采用以下哪一种方式：

**方案 A（开发侧建议）：ch06 专属提交/compaction 规则**

- 通用 compaction 继续服务其他章节；
- ch06 step-1 submit 只执行 stale 标记与 profile likes 失效，不执行 likes 写入；
- ch06 step-2 submit 只取最新、非 stale 的 step-2 结构化 likes，显式覆盖 profile likes；
- ch06 step-1/step-2 的其他允许字段（如 commentary）按现有规则处理；
- 不让通用 compaction 对 ch06 两个同名 likes 做隐式合并。

**方案 B：通用 compaction 增加声明式字段优先级**

如果选择该方案，请在 config 或其他唯一权威契约中明确：

- 同名字段的步骤优先级；
- stale 结果是否自动排除；
- step-1 中间结果是否允许作为 profile 字段；
- 其他章节是否会受新的优先级机制影响；
- 如何防止现有 ch03/ch05 行为回归。

开发侧建议采用方案 A，因为它只影响 ch06 的特殊两级同名字段，不改变全局 compaction 语义。

### 2.4 验收用例建议

设计侧确认后，开发侧将至少覆盖：

1. 只运行 step-1：profile 不新增/不写入 step-1 likes；
2. step-1 saved 后：profile 不写入 step-1 likes；
3. step-1 submit：旧 step-2 stale，profile likes 变为 `[]`；
4. step-2 run/saved：profile 仍保持 `[]`；
5. step-2 submit：profile 只写入结构化 step-2 likes；
6. step-2 为空数组提交或校验失败：不把中间领域 likes 写入 profile；
7. step-1 重提交后：导师/ch07 不能读取旧 step-2 likes；
8. step-2 新提交后：导师/ch07 只读取新的结构化 likes；
9. 旧 ch03 likes 存在但没有有效 ch06 step-2：ch07 仍然阻断。
