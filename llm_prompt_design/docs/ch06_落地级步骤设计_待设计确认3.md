## 2. 待设计侧确认的问题

### Q1. q1–q5 与 `passion_questions` 的必填关系

设计侧第二轮回复 §1.2 说明：30 问是“当 5 个问题不够用时的追加题库”，并提到将 30 问放在 step-1 是为了避免用户只使用 30 问时 step-1 没有输出。

但当前 canonical config 仍把 q1–q5 全部声明为必填：

- `config/chapters/chapter_config_ch06.json` step-1 `input_schema` 中 q1–q5 均为 `required: true`。
- `passion_questions` 为 `required: false`。

这会产生一个实际矛盾：

- 设计侧理由似乎允许“只回答 30 问也能发现喜欢的领域”；
- 当前 config/运行校验却要求 q1–q5 五项全部填写，用户无法只依靠 30 问运行 step-1。

请设计侧明确最终规则，二选一或给出第三种明确规则：

#### 方案 A：q1–q5 继续全部必填（开发侧倾向）

- q1–q5 是本章主流程的固定五问；
- 30 问只是追加素材，不能替代 q1–q5；
- config 当前 `required: true` 保持不变；
- UI 文案明确“先回答五问；如果素材不足，再打开 30 问补充”。

#### 方案 B：q1–q5 改为可选，至少有一类证据即可运行

- q1–q5 全部改为 `required: false`；
- 后端运行前校验：q1–q5 与 `passion_questions` 合并后至少有一条非空用户证据；
- UI 文案说明可以只回答 30 问，但建议优先完成五问。

需要同时确认：

1. 如果采用方案 B，“至少一条证据”的判定是按一个非空字段，还是至少回答几道题？
2. 空答案、只输入空格、只保存题目未填写回答，是否都视为无证据？
3. 运行后如果用户删除所有 q1–q5，只保留 30 问回答，是否允许重新运行？

开发侧建议采用方案 A，以保持当前 config 与“30 问为追加题库”的设计口径一致；但不能自行替设计侧拍板。

### Q2. “已过期”结果的状态表示与下游隔离

设计侧第二轮回复确认：step-1 重新提交后，step-2 的既有 `saved` / `submitted` 结果标记为“已过期，请重新运行第二步”，不自动删除、不自动合并。

但当前数据库状态约束只允许：

```text
draft / saved / submitted / failed
```

位置：`platform/backend/app/db.py` 的 `step_runs.status` CHECK 约束。

请明确“已过期”的实现方式：

#### 方案 A：新增 `expired` 状态（开发侧不建议直接采用）

- 扩展数据库 CHECK 约束；
- 修改所有按 `saved/submitted/failed` 枚举处理的接口、前端和测试；
- 需要明确 expired 是否仍可查看、是否可以重新编辑、是否可以再次提交。

#### 方案 B：保留原状态，增加依赖版本/过期标记（开发侧建议）

例如在 `step_runs` 已有字段或 JSON 中记录：

```json
{
  "source_step_id": "step-1",
  "source_run_id": "...",
  "source_submitted_at": "...",
  "stale": true
}
```

此方案不改变通用状态机，但需要设计侧确认：

- `stale` 放在 `referenced_outputs`、`user_answers`、`parsed_output`，还是新增数据库列；
- step-2 的 `saved/submitted` 旧结果是否仍显示为只读历史；
- stale 的 step-2 是否禁止作为导师上下文和 ch07 下游输入；
- step-2 重新运行成功后，旧结果如何恢复为当前有效结果。

#### 必须明确的下游行为

step-2 已 `submitted` 的 `likes` 通常已经进入 `learner_profile`，可能被导师或 ch07 读取。因此需要明确：

1. step-1 新提交后，旧 step-2 `likes` 是否立即从 `learner_profile` 撤回/替换？
2. 在 step-2 重跑完成前，导师是否暂时不能读取旧 likes？
3. ch07 是否应把 step-2 标记 stale 视为上游未就绪并阻断/提示？
4. 如果旧 step-2 结果保留在历史 step_run 中，哪些读取路径必须只选择“最新且未过期”的结果？

开发侧建议：

- 不新增 `expired` 通用状态，使用明确的依赖指纹或 `stale` 标记；
- stale 的 step-2 不得进入导师和 ch07；
- 旧 `learner_profile.likes` 在 step-1 新提交后应被清除或标记不可用，直到新的 step-2 提交完成；
- 重新提交 step-2 后，只允许最新且依赖当前 step-1 submitted run 的结果进入 profile 和下游。

请设计侧确认是否采纳，或者明确另一套完整方案。

### Q3. `sources` 的来源范围、格式与字段说明

设计侧第二轮回复允许 30 问产生的来源写成 `q{order}`，例如 `q61`：

```json
"sources": ["q1", "q3", "q61"]
```

但当前 config 与 PRD 的字段说明仍写成“来源（Q1–Q5）”：

- `config/chapters/chapter_config_ch06.json` step-2 `sources` label；
- `PRD-ch6.md` 的字段表和 step-2 Prompt 约束；
- PRD 示例仍只展示 `q1`、`q3`、`q4`。

请统一确认：

1. step-2 `sources` 是否允许同时包含：
   - q1–q5：`q1` … `q5`；
   - 30 问：`q61` … `q90`。
2. 是否固定使用小写 `q` 加全局题库序号，例如 `q61`，不使用 `61`、`热情-1` 或题目文本？
3. step-1 输出的单值 `source` 是否也使用同一格式；如果某个领域来自多个问题，step-1 是否允许 `source` 为数组，还是保持单值并由 step-2 统一归并为 `sources` 数组？
4. `sources` 是否允许为空数组；如果 LLM 无法可靠溯源，是否返回空数组而不能猜测？
5. UI 是否需要显示 30 问来源，还是只在数据层保留？

开发侧建议：统一为小写 `q{global_q_order}`，允许 q1–q5 与 q61–q90 混合；无法可靠溯源时返回空数组，不造假；step-1 保持现有单值 `source`，step-2 输出数组 `sources`。

### Q4. PRD 是否完整同步 `passion_questions` 与 `passion_seeds`

设计侧回复声明 PRD 已修复 Q3 的 `work_purpose/Q27` 残留，但 PRD 的工作流部分仍未完整描述本轮新增输入字段：

- step-1 的 `input_schema` 仍概括为“5 个 text 必填字段 q1–q5”；
- step-2 的 `input_schema` 仍只列 `reference_talents`；
- 30 问仍只作为“题库抽屉”描述，没有说明回答如何填入 `passion_questions`；
- `passion_seeds` 的持久化和 Prompt 注入边界没有在 PRD 工作流契约中完整体现。

虽然 PRD 第 0 节声明“config 是权威契约”，但 PRD 自身仍会被产品、测试和后续开发阅读；继续保留不完整描述会导致再次出现前一步/辅助输入没有真正进入后一步的实现遗漏。

请设计侧确认是否同步修改 PRD：

1. step-1 输入改为“q1–q5 + 可选 `passion_questions`”；
2. step-2 输入明确列出可选 `reference_talents` + `passion_seeds`；
3. 明确 30 问回答由题库服务保存到 `book_notes`，运行前按 `q_order` 注入 step-1 `user_answers`；
4. 明确 `passion_questions` 不直接写入最终 profile，仅通过 step-1 `likes` 间接影响下游；
5. 明确 step-1 submitted-only 级联与 step-1 重跑后 step-2 stale/过期处理；
6. 明确 `passion_seeds` 与 `reference_talents` 只作为 step-2 分析上下文，不直接写入最终 `likes`（除非 LLM 根据用户证据生成了对应条目）。
