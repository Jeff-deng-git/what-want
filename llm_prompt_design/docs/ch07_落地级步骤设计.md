## §0 全书位置与角色

ch07 是全书第 7 章，也是**唯一收敛章**：把前序三章 ch04/ch05/ch06（ch04 重要的事 / ch05 擅长的事 / ch06 喜欢的事）的产出组合成"想做的事"。后续 ch08 施展魔法将消费本章 `ideal_works`。

- 上游：ch04 `work_purpose`/`values`、ch05 `talents`、ch06 `likes`
- 下游：ch08 消费 `ideal_works`
- 公式（原书）：喜欢的事 × 擅长的事 = 想做的事候选；工作目的（ch4）筛选成"真正/兴趣"两桶。

## §1 目标

让用户在"放弃为将来"的心态下，先用"喜欢×擅长"自由组合出一批"想做的事"假设（数量优先），再用第四章工作目的筛出"真正想做的事"与"作为兴趣的想做的事"，并给出可行动的复盘计划（螺旋上升）。

## §2 一步 vs 多步

**多步（2 步级联）**，与 ch04–ch06 同范式。
- step-1 组合（喜欢×擅长 → 候选）
- step-2 筛选定稿（工作目的 → 分桶 + 下一步行动）

> 不采用旧稿"单步"形态：原书明确两段流程，单步丢失"组合→筛选"可编辑分段。

## §3 流程图

```
[ch4 work_purpose] ─┐
[ch5 talents ◎〇△] ─┼─(mentor_hooks 带入导师上下文)─→ step-1 组合(career_counselor)
[ch6 likes·方面]  ─┘                                          │  ideal_works(候选)
                                                            ▼
                                              step-2 筛选定稿(mentor, 用 work_purpose)
                                                            │  ideal_works(带 bucket)
                                                            ▼
                                              真正想做的事 / 作为兴趣的想做的事 + next_action
```

## §4 逐阶段

### 阶段一 step-1 组合（career_counselor）
- 输入：导师上下文 `talents`（ch5，含◎〇△）、`likes`（ch6，含领域/方面）。无独立 input_schema 字段；跨章数据经 `step_context.references` + `mentor_hooks.references` 注入（step-1 组合需把上游读进 step prompt，故必须在 `step_context` 声明——见 §8.3，这是 ch07 相对 ch03/ch05「仅 mentor_hooks」惯例的扩展点）。
- 处理：LLM 交叉组合 8–15 条候选，每条 `like_source`/`strength_source` 溯源到具体上游项；数量优先、允许假设；不臆造。
- 产出：`ideal_works`（editable_list，含 title/like_source/strength_source/bucket=未定/locked）+ `commentary`。

### 阶段二 step-2 筛选定稿（mentor）
- 输入：step-1 `ideal_works`（references.from_exercise）+ 步骤上下文 + 导师上下文 `work_purpose`/`values`（ch4）。
- 处理：LLM 逐条给分桶建议（真正/兴趣/未定）并说理由；不替用户定档；保留 `locked=true` 项；输出 `next_action` 复盘计划（先试最想做的假设，行动后回顾修正）。
- 产出：`ideal_works`（带 bucket）+ `commentary` + `next_action`。

## §6 锁定类型

- 运行时锁定 = 整步提交态：`edit_output` 在 submitted 态返回 409，须先 `submit_step`；与 ch02–ch06 同构。
- `lockable`（schema 意图声明）：`ideal_works` 每项可 `locked`，LLM 不覆盖；`readonly` 仅用于 `commentary`/`next_action`（LLM 产出，用户只读）。
- 勿锚 legacy `step_runner._merge_with_locked`（已不消费）。

## §8 数据表与字段

### 8.1 持久化键
- **`ideal_works`**：ch07 唯一新增键，落 `learner_profiles.profile_json`。
- 当前**不在** `compaction.py` 白名单 → 开发侧在 `PROFILE_FIELDS`/`STRUCTURED_FIELDS`/`MANDATORY_DOWNSTREAM_FIELDS` 三处加入（仅新增一个已存在 profile_json 内的键，**ideal_works 自身零新增表/列**），并 reseed 消除 DRIFT。
- **`stale` 列沿用（ch06 第六轮拍板）**：ch07 全部 step-run 读取须带 `AND stale=0`，沿用 ch06 在 `step_runs` 表新增的 `stale INTEGER NOT NULL DEFAULT 0` 列（后端 `init_db()` 幂等补列）；ch07 step-1 重提交时须令旧 step-2 `stale=1` 且 `profile.ideal_works=[]`（见 §10 门禁与 stale 传播）。
- 旧稿曾用 `intersection`——该键属 **ch03**（三清单字面交集、早期"想做的事"假设），复用会覆盖 ch03 产物，故弃用，改用独立键 `ideal_works`。
- **`ideal_works` canonical 写入规则（仿 ch06 §8.8 方案 A）**：`profile.ideal_works` 以**最新、非 stale 的 step-2 提交**为准；step-1 的 `ideal_works`（bucket=未定）仅作 step-2 级联输入，**不直接覆盖 profile**；最终由 step-2 提交显式覆盖写入。step-1 重提交时旧 step-2 `stale=1` 且 `profile.ideal_works=[]`（见 §10）。通用 compaction `_flatten_outputs` 按字段后者覆盖前者，故 ch07 提交逻辑须绕过通用合并、用显式非-stale 选取（同 ch06 §8.8）。

### 8.2 ideal_works 项形态
`{title, like_source(只读), strength_source(只读), bucket(枚举), locked}`

### 8.3 三路上下文（与 ch03 解耦一致）
- `step_context.references = [talents, likes, work_purpose, values]`（ch7 步骤分析组合/筛选需读上游，与 mentor_hooks 同键；assembler 注跨章 profile 入 step prompt 只读 step_context.references，故必须在此声明）
- `mentor_hooks.references = [talents, likes, work_purpose, values]`
- `ui_context.references = []`（ch7 无独立 UI 清单载体）

### 8.4 状态机
`/run`（运行 LLM → saved 草稿）→ 编辑/锁定 → `/submit`（submitted，不调 LLM，edit_output 409）。

### 8.5 下游（ch8）
ch08 是独立流程图决策导航页（`page_type:flowchart`），**不消费 `ideal_works`**；与 ch07 的关联改为**真实跳转**（dp-4「是」→ ch07 组合 exercise；dp-refine「去提炼」→ ch07 筛选定稿 exercise），而非读取 profile 字段。详见 `ch08_落地级步骤设计.md` §10。

### 8.6 草稿持久化契约（与 ch05 §8.6 同构）
- 草稿跨刷新/重新进入保留，显示"上次保存于"时间戳。
- 草稿不进 submitted / 下游 / 导师 / profile；保存失败明示。
- `ideal_works` 草稿与 `locked` 状态隔离于 `user_answers`/draft run。
- 回归测试：刷新后草稿恢复、锁定项不被覆盖、保存失败有提示。

## §9 设计判断

1. **新键 `ideal_works` 而非复用 `intersection`/`success_statement`**：前者与 ch3 冲突，后者语义偏单句陈述；`ideal_works` 直白且与书词汇一致。
2. **2 步级联**：对应原书两段 + 与 ch04–ch06 范式一致。
3. **角色不新增**：组合/筛选差异由 config `instruction`/`method` 表达，守 ch03 规则。
4. **跨章注入 `step_context` + `mentor_hooks`（ch07 是首例扩展）**：assembler 把跨章 profile 注入 step prompt 时**只读 `step_context.references`**（实测 `assembler.py:543`：`profile_refs` 取自 step_context，step_context 存在时绝不回退 mentor_hooks）。ch03/ch05/ch06 的 step prompt 不需上游数据，故沿用「仅 mentor_hooks」惯例未暴露问题；ch07 step-1 是首个「组合 step 需要读上游」的章，必须把 `talents/likes/work_purpose/values` 同时写进 `step_context.references` 与 `mentor_hooks.references`，否则 step LLM 拿不到上游。这是 ch07 与 ch03/ch05 跨章惯例的关键差异，已在 §8.3 显式声明。

### 10.1.1 进入门禁双校验（stale 维度，仿 ch06 §8.7）
- 进入 ch7 前 `context_requirements` 须校验：
  (a) ch04 step-5 `submitted & stale=0` 且 `profile.work_purpose`/`values` 非空；
  (b) ch05 step-2 `submitted & stale=0` 且 `profile.talents` 非空；

- 任一缺失整章锁定（半透明遮罩 + "请先完成第 X 章"卡 + 直达按钮）。上游章重提交使旧 run `stale=1` 后，ch07 门禁须即时回退为锁定态，不能误判"已就绪"。

### 10.1.2 ch07 内部 stale 传播（仿 ch06 §8.7 三动作事务）
- 场景：ch07 step-1 被重提交。事务三动作（任一失败整体回滚）：① 写新 step-1 run；② 旧 ch07 step-2 `stale=1`；③ `profile.ideal_works=[]`。
- 新 step-2 提交须显式选**最新非 stale** 的 step-1 `ideal_works` + 自身输出；提交成功才覆盖 profile，失败保持 `[]`。
- 读取统一语义：`status='submitted' AND stale=0`（上游 ch06 likes / ch05 talents / ch04 values,work_purpose，及自身 step-2 读 step-1 的 `references.from_exercise` 解析路径均须带此过滤）。
