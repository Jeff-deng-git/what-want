## 2. `likes` 的权威来源在 ch03、ch06、ch07 之间存在冲突

这是本轮最重要的问题。

### 2.1 当前代码/配置事实

当前工作区存在以下事实：

1. `config/chapters/chapter_config_ch03.json` 仍定义并输出 `likes`；
2. `config/chapters/chapter_config_ch06.json` 也定义并输出 `likes`，但 ch06 的结构已经升级为：
   - step-1：领域级 `{text, locked, source}`；
   - step-2：`{field, aspects[], linked_strengths[], sources[], locked}`；
3. `platform/backend/app/services/compaction.py` 使用同一个 profile 键 `likes` 保存结果；
4. `config/chapters/chapter_config_ch07.json` 的 step-1 明确要求读取 ch6 的 `likes`；
5. `config/chapters/chapter_config_ch07.json` 的 `mentor_hooks.references` 也包含 `likes`；
6. 但 `platform/backend/app/runtime/context_requirements.py` 当前仍把 ch03 作为 `likes` 的生产者：

```python
CHAPTER_UPSTREAM_REQUIREMENTS = {
    "ch07": {
        "ch03": ("likes", "talents", "importance"),
        "ch04": ("work_purpose",),
        "ch05": ("talents",),
    },
}
```

因此目前存在两个潜在解释：

- ch03 的 `likes` 是旧的/早期的喜欢之事结果，ch06 应覆盖它；
- ch03 和 ch06 都是正式生产者，但需要合并或区分来源。

设计侧回复目前只写“ch06 使用 `likes`”，尚未明确这个冲突的最终业务语义。

### 2.2 请设计侧拍板唯一来源规则

请明确采用哪一种方案。

#### 方案 A：ch06 成为 ch07 的唯一 `likes` 来源（开发侧建议）

- ch03 的 `likes` 保留为历史/早期探索结果，不作为 ch07 的正式输入；
- ch06 step-2 成功提交后，覆盖当前 `learner_profile.likes`；
- ch06 step-1 重提交时，旧 ch06 step-2 结果 stale，当前 profile `likes=[]`；
- ch07 在 ch06 没有最新有效 step-2 时必须阻断；
- `context_requirements.py` 的 ch07 上游正式改为包含：

```python
"ch06": ("likes",)
```

- ch03 是否继续作为 ch07 的其他字段来源，需单独保留明确字段，例如 `importance` / `talents`，但不能继续以 ch03 的 `likes` 证明 ch06 已完成。

#### 方案 B：ch03 与 ch06 的 `likes` 合并

如果选择该方案，请明确：

- 合并是覆盖、追加，还是去重合并；
- ch03 的扁平条目如何转换为 ch06 的 `field/aspects` 结构；
- ch03 的旧数据是否可以被 ch07 直接消费；
- ch06 stale 时是否允许继续使用 ch03 的 likes；
- 哪个结果决定 ch07 的“第六章已完成”状态。

开发侧不建议默认采用，因为会让 ch07 在 ch06 失效时继续消费旧的 likes，违反第四轮确认的 stale 隔离目标。

#### 方案 C：ch03 与 ch06 使用不同 profile 字段

例如：

```json
{
  "likes": [...],
  "passion_likes": [...]
}
```

如果选择该方案，请重新确认 ch06 的下游键、compaction 白名单、ch07 config、导师 references 和已有 profile 兼容策略。该方案会扩大 profile 契约，不能由开发侧自行决定。

### 2.3 还需要确认历史数据迁移/兼容规则

无论选择哪种方案，都请明确已有数据的处理：

1. 已有 ch03 `likes` 是否继续保留在 profile；
2. 新增 ch06 之前，profile 中已有的 `likes` 是否视为“旧值”，不能证明 ch06 完成；
3. ch06 首次提交后是否无条件覆盖旧 `likes`；
4. ch07 在只有旧 ch03 `likes`、没有有效 ch06 step-2 时是否必须阻断；
5. 是否需要一次性清理/迁移历史 profile，还是运行时通过“有效 ch06 step-2 + 非 stale”判断即可；
6. 历史 ch03 `likes` 是否允许在 UI 中展示，但不能进入 ch07、导师或 summary。

### 2.4 开发侧建议的最终口径

建议设计侧确认以下规则：

> ch06 step-2 是 ch07 当前 `likes` 的唯一正式来源。ch03 的旧 `likes` 仅作为历史字段保留，不参与 ch07 完成判定、导师上下文、summary 或 ch07 LLM 输入。ch06 step-2 只有在 `status='submitted' AND stale=0` 且输出 `likes` 为非空数组时，才可以覆盖当前 profile `likes` 并被下游消费。

## 3. stale 过滤尚未覆盖所有实际读取路径

第四轮回复确认统一读取：

```sql
status = 'submitted' AND stale = 0
```

但当前代码中仍有多处只筛选 `status='submitted'`：

### 3.1 导师 step 上下文

`platform/backend/app/routers/chat.py`：

- `_load_step_context` 当前查询只包含 `status='submitted'`；
- `_load_submitted_chapter_context` 当前查询只包含 `status='submitted'`。

需要确认：stale 的历史 step-2 是否完全不能进入导师上下文，包括：

- 当前步骤上下文；
- 本章已提交步骤摘要；
- 导师首次进入时的 profile/step 混合上下文；
- 导师强制 compaction 或刷新 profile 的输入。

开发侧建议：所有面向导师的 step-run 查询统一增加 `stale=0`，并按“最新有效 submitted run”读取；stale 历史只允许在专门的历史查看接口中返回。

### 3.2 章节级级联输入

`platform/backend/app/runtime/agent.py` 的 `_load_prior_outputs` 当前按 `status='submitted'` 读取章节内上游 step。

需要确认：

- ch06 step-2 读取 step-1 时，是否也必须加入 `stale=0`；
- ch07 或其他未来章节通过 step-run 读取 ch06 输出时，是否统一加入 `stale=0`；
- “submitted-only” 是否已经正式升级为“submitted-and-not-stale-only”。

开发侧建议将所有 `references.from_exercise` 的读取语义统一固定为：

> 只读取 `status='submitted' AND stale=0` 的最新结果；找不到时视为上游未完成。

### 3.3 `_maybe_compact` 的 profile 写入来源

`platform/backend/app/routers/steps.py` 的 `_maybe_compact` 当前读取每个步骤最新的 `submitted` run，但没有 stale 过滤。

需要确认：

- compaction 是否只允许消费 `stale=0`；
- ch06 step-1 重提交后，旧 step-2 stale 结果是否绝对不能再次触发 profile 写入；
- ch06 新 step-2 提交成功时，是否只用新的非 stale step-2 输出覆盖 `likes`，而不是把 step-1 与 step-2 两个 `likes` 一起交给 compaction 让其自行决定覆盖顺序。

开发侧建议：

- `_maybe_compact` 的所有步骤查询均增加 `stale=0`；
- ch06 需要明确 compaction 输入只使用 step-2 的正式结构化 `likes`，step-1 的领域草稿不直接写入最终 profile；
- 如果一个章节内多个步骤输出同名字段，覆盖顺序必须在契约中固定，不能依赖查询顺序或字典后写覆盖的隐式行为。

### 3.4 ch07 上游状态检查

`platform/backend/app/runtime/context_requirements.py` 当前：

- 没有登记 ch06；
- 查询 producer step 时只按 `status='submitted'`；
- 只检查 profile 字段是否非空，没有检查 ch06 step-2 是否存在最新 `stale=0` run。

请设计侧明确是否将 ch07 门禁固定为双校验：

1. 当前 profile `likes` 为非空数组；
2. ch06 step-2 存在 `status='submitted' AND stale=0` 的最新结果。

两者任一失败均阻断 ch07，并提示“请先完成第六章”。

## 4. summary 是否属于 stale 隔离范围需要明确

第四轮回复将 stale 结果列入“不能进入导师 / summary / ch07 / compaction”，但当前 summary 的实际实现需要区分两种语义：

### 4.1 书籍章节摘要

`platform/backend/app/routers/summary.py` 的主要路径调用 `run_summary`，核心输入是章节原文；这类摘要本身不需要 ch06 用户 `likes`，也不应因为 profile 中 likes stale 而被无条件阻断。

### 4.2 可能包含用户 profile 的摘要

`platform/backend/app/runtime/agent.py` 的 `run_summary` 会加载 profile 并传给 `build_summary_prompt`。当前需要确认：

- `build_summary_prompt` 是否把 `likes` 注入 summary prompt；
- 如果注入，stale 结果必须被过滤或 summary 必须在 likes stale 时阻断；
- 如果不注入，summary 不应被列为 stale 隔离消费方；
- 章节书籍摘要的生成与 ch06 完成状态是否应完全解耦。

### 4.3 开发侧建议

建议设计侧确认：

> 当前 summary 功能是书籍正文摘要，不消费用户 ch06 `likes`；stale 隔离范围应从 summary 中移除。若未来新增“基于用户 profile 的个性化摘要”，必须另定义 profile freshness 门禁，不默认继承本规则。
