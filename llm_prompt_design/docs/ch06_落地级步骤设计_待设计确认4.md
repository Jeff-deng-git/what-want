## 1. 数据库迁移规则与落地文档存在冲突

### 1.1 当前设计侧回复的最终规则

第三轮设计侧回复已经明确采用 stale 方案：

```sql
step_runs.stale INTEGER DEFAULT 0
```

并要求：

- `stale` 是 `step_runs` 的独立布尔列；
- 不扩展 `status` 的 `draft/saved/submitted/failed` 枚举；
- `referenced_outputs` 增加上游依赖指纹：

```json
{
  "source_step_id": "step-1",
  "source_run_id": "<step-1 submitted run id>",
  "source_submitted_at": "<timestamp>"
}
```

- step-1 重新提交后，已有 step-2 的 `saved/submitted` 结果设置为 `stale=1`；
- 导师、profile compaction 和 ch07 只允许读取最新的 `submitted` 且 `stale=0` 的 step-2 结果。

### 1.2 与落地文档的冲突

`ch06_落地级步骤设计.md` 当前仍保留以下旧表述：

- §0：**零新建数据库表/列/迁移**；
- §8.1：**持久化结论（零迁移）**，并写明「零新增表/列/迁移」；
- §8.4：**不新建数据库表/列、无表结构迁移**。

这与第三轮回复中“必须新增 `step_runs.stale` 列并执行一次迁移”的规则直接矛盾。虽然文档声明 config 是运行时权威源，但数据库迁移并不属于 config 字段契约，开发仍需要一个唯一且明确的数据库实施口径。

### 1.3 请设计侧确认并同步的唯一表述

请确认是否采用以下修订口径：

> ch06 不新增业务表，也不新增 `likes` 专用表；但为支持上游重提交后的过期隔离，在既有 `step_runs` 表新增 `stale INTEGER NOT NULL DEFAULT 0` 列，并执行一次向后兼容的 SQLite 迁移。`referenced_outputs` 继续复用既有 JSON 字段保存依赖指纹。

若该口径正确，请同步修改落地文档中的：

- §0 的“零新建数据库表/列/迁移”；
- §8.1 的标题与迁移结论；
- §8.4 的改动范围说明；
- 其他仍使用“零迁移”“无 schema 迁移”的相关表述。

同时请明确迁移要求：

1. 已有数据库启动时自动补列，还是由独立迁移脚本执行；
2. 迁移是否必须幂等（重复启动不能报错）；
3. 旧数据补列后的默认值是否统一为 `0`；
4. 现有 `step_runs` 查询/插入接口是否需要兼容没有该列的旧数据库。

### 1.4 开发侧建议的验收标准

- 新数据库初始化后存在 `step_runs.stale`，默认值为 `0`；
- 已有数据库升级后不丢失任何 `step_runs` 数据；
- 重复执行启动迁移不会报错；
- 旧 run 的 `stale` 默认为 `0`；
- `status` 的既有状态机不发生变化；
- 有对应的迁移或数据库契约测试。

## 2. `learner_profile.likes` 的失效方式与事务边界未完全确定

### 2.1 当前设计侧回复的规则

第三轮回复要求：

- step-1 重新 `submitted` 后，旧 step-2 `likes` 立即从 `learner_profile` 失效；
- 在新的 step-2 提交前，导师不能读取旧 likes；
- ch07 必须把 stale 视为第六章上游未就绪；
- 新 step-2 成功提交后，新的 likes 才重新进入 profile、导师和 ch07。

但当前使用了“清除/标记不可用”的并列表述，没有指定唯一数据形态。

### 2.2 需要设计侧拍板的具体问题

请明确 `learner_profile` 在 step-1 重提交后采用以下哪一种 canonical 表示：

**方案 A：删除当前 likes 字段**

```json
{
  "values": [...],
  "talents": [...]
}
```

优点是语义直接，读取方按字段缺失视为未完成；缺点是无法从 profile 中保留上一版结果。

**方案 B：当前 likes 置为空数组**

```json
{
  "likes": []
}
```

优点是 schema 稳定；缺点是需要确保空数组不会被误判为已经完成第六章。

**方案 C：当前 likes 保留，但增加 profile 级失效信息**

```json
{
  "likes": [...],
  "likes_status": "stale"
}
```

优点是能保留当前可见数据；缺点是所有导师、summary、ch07 读取方都必须实现一致的状态门禁，且与 `step_runs.stale` 存在双重状态来源。

**方案 D：当前 likes 清空，旧值单独存历史字段**

```json
{
  "likes": [],
  "likes_history": [...]
}
```

优点是同时满足当前不可消费与历史查看；缺点是会扩大 profile 契约，需要明确历史字段是否永久保留及其读取边界。

开发侧建议优先选择 **方案 B**：`learner_profile.likes = []`，不增加 profile 新字段；历史版本仍由 `step_runs` 中 `stale=1` 的结果保留并只读展示。这样 profile 只有一个当前值来源，导师与 ch07 不会因新增 profile 状态字段而产生第二套门禁逻辑。

### 2.3 需要明确的事务与恢复语义

请设计侧进一步确认：

1. step-1 重提交时，以下动作是否必须在同一数据库事务中完成：
   - 写入新的 step-1 `submitted` run；
   - 将既有 step-2 `saved/submitted` runs 标记为 `stale=1`；
   - 使 `learner_profile.likes` 失效。
2. 如果其中任一动作失败，是否整体回滚，避免出现“step-1 已是新版本、step-2 已 stale，但 profile 仍保留旧 likes”的中间状态。
3. 新 step-2 提交失败时，profile 是否保持失效状态，直到新 step-2 成功提交；开发侧建议是保持失效，不恢复旧 likes。
4. 用户只重新运行 step-1 但尚未提交时，是否不触发 stale 和 profile 失效；开发侧建议是**只有 step-1 成功 `/submit` 才触发**。
5. 用户重新提交 step-1 后，页面是否需要显示明确提示，例如：
   > 你更新了第一步答案，第二步的旧分析已标记为历史记录，请重新运行并提交第二步。

### 2.4 读取优先级也请一并固定

请明确以下读取规则是否统一为：

- `step_runs`：按 `status='submitted' AND stale=0`，再取最新 run；
- `learner_profile`：只读取当前 `likes`，空值/缺失均视为第六章尚未完成；
- stale 的历史 step-2 结果：仅用于历史查看，不进入导师、summary、ch07 或 compaction；
- 新 step-2 成功提交后，由该次提交覆盖写入当前 `learner_profile.likes`。
